# CEO Plan: 현장 검증에서 모임의 결제 의식으로

## Vision

누가낼래는 일반적인 모임 장부가 아니라, 결제를 먼저 한 총무 한 명이 토스에서 열어 참가자 전원의 가입 없이 한 기기로 3분 안에 끝내는 게임형 정산 의식이다. 재미가 앱을 열게 하고, 설명 가능한 계산과 공유가 끝까지 쓰게 하며, 모임 기억이 다음 만남의 재사용 이유가 된다.

### 10x Check

총무가 최근 모임을 누르고 금액만 입력하면, 앱이 지난번과 겹치지 않으면서 3분 안에 끝나는 게임을 추천한다. 휴대폰을 차례로 넘기면 각 참가자가 자신의 차례를 확인하고 플레이한다. 마지막에는 게임 결과, 적용 규칙, 참여자별 금액, 합계 일치를 모두가 이해하고 단톡방에 공유한다. 다음 모임에서는 지난 기억이 한 줄로 돌아오고 새로운 게임을 추천한다.

### Platonic Ideal

사용자는 기능을 탐색하지 않는다. 총무는 최근 모임을 한 번 누르고 금액만 입력한다. 참가자는 자신의 차례 외에는 아무것도 배울 필요가 없다. 결과는 재미있게 공개되지만 돈의 계산은 차분하고 검증 가능하다. 기록은 사람을 낙인찍거나 결과를 조작하지 않고, 다음 만남을 더 빠르고 새롭게 만드는 데만 쓰인다.

## Chosen Implementation Approach

현장 검증 준비 정비를 실행 기반으로 유지한다. 실패 테스트, 입력 범위, 핵심 측정, 저장·공유 실기기 검증을 먼저 끝낸다. 대규모 `App.jsx` 재작성이나 서버 기반 장부는 이번 계획의 기반이 아니다. 승인된 확장은 두 단계로 출시한다.

## Architecture Contract

`App.jsx`는 화면 조립과 네이티브 브리지 연결만 담당하는 얇은 셸로 점진적으로 축소한다. 전면 재작성은 하지 않고 기능을 수정하는 시점에만 다음 경계를 추출한다.

```text
Toss App / Sandbox
  ├── Storage · Share · Clipboard · Image Save
  └── React App Shell
      ├── settlement/flow-controller
      │   ├── setup + recent-group UI
      │   ├── handoff + game UI
      │   └── result + receipt UI
      ├── games
      │   ├── catalog · scoring · session · settlement
      │   └── recommendation (2차 B)
      ├── results
      │   ├── receipt projection
      │   └── share fallbacks
      ├── storage
      │   ├── repository
      │   ├── identity + migration (2차 A)
      │   └── fairness + memory projection (2차 C/D)
      └── external boundaries
          ├── Amplitude consent gate
          ├── AppsInToss ads
          └── feature flags
```

의존성은 UI → flow-controller → 순수 도메인 → repository adapter 방향으로만 흐른다. 게임·계산·추천·영수증 투영은 React와 네이티브 브리지를 import하지 않는다. Storage·Amplitude·Share는 인터페이스 뒤에 두어 단위 테스트에서 메모리 구현으로 교체한다.

```text
Happy: 모임 → 금액 → 게임 → 합계 검증 → 저장 → 공유
Nil:   모임 미선택 → 새 모임 입력
Empty: 최근 기록 0건 → 새 정산 CTA만 표시
Error: Storage 실패 → 일회성 정산 유지
       합계 불일치 → 저장·공유 차단
       Share 실패 → 이미지 → 텍스트 폴백
```

```text
BOOT → CONSENT → HOME → SETUP → HANDOFF → COUNTDOWN → PLAY → TURN_RESULT
                         ↑                    │             │
                         └──── 새 정산 ──────┘             ├─ 다음 참여자 → HANDOFF
                                                          └─ 마지막 → CALCULATED
CALCULATED ── 합계 일치 ─→ SAVED_OR_EPHEMERAL → SHARE_READY → SHARED
CALCULATED ── 합계 불일치 → BLOCKED
```

- `TURN_RESULT` 없이 다음 참가자로 이동할 수 없고, 합계 불변식을 통과하지 않은 결과는 저장·공유할 수 없다.
- 10배 기록에서는 최근 6건과 최근 모임 인덱스만 읽어 선형 전체 스캔을 피한다. 100배 기록에서는 하나의 거대한 JSON 배열이 Storage 쓰기·마이그레이션의 첫 병목이므로 그룹·정산 인덱스를 키 단위로 분리한다.
- 단일 장애점은 Storage 활성 매니페스트와 계산 불변식이다. 전자는 체크섬 후보와 v1 백업으로, 후자는 저장·공유 차단으로 실패를 격리한다.
- 새 서버·인증·외부 쓰기 API는 추가하지 않는다. 데이터 변경 권한은 같은 기기의 현재 사용자에게만 있으며 모든 변경은 로컬 삭제·롤백 계약을 따른다.
- 2차 A/B/C/D는 각각 `VITE_ENABLE_*` 빌드타임 플래그를 사용한다. 프로덕션에서 임의로 바꾸는 로컬 숨김 플래그나 원격 설정 서비스는 추가하지 않는다.
- 1차 장애는 이전 앱 빌드로 되돌리고, 2차 UI 장애는 해당 빌드 플래그를 끈 수정 빌드로 되돌린다. 2차 데이터 장애는 플래그 비활성화와 함께 활성 매니페스트를 검증된 v1 또는 직전 v2 키로 전환한다. 롤백 목표 시간은 수정 빌드 준비 30분 이내이며 사용자 데이터는 삭제하지 않는다.

| Integration | Realistic failure | Isolation |
|---|---|---|
| AppsInToss Storage | 쓰기 거부·손상 JSON·중간 종료 | 직렬 큐, 후보 read-back, 활성 포인터 유지, 일회성 정산 |
| Share / save / clipboard | OS 취소·브리지 미지원·모든 폴백 실패 | 취소와 실패 분리, 결과 유지, 다음 폴백 또는 재시도 |
| Amplitude | SDK 로드·전송 실패 | 핵심 흐름과 분리, 동의 전 미초기화, 전송 실패 비차단 |
| Ads | SDK 미지원·로드 실패 | 광고만 생략하고 정산 지속 |
| Migration | quota·참조 무결성·체크섬 실패 | v1 활성 유지, 후보 폐기, 백업 보존 |

## Accepted Scope

### 1차: 현장 검증 가능한 코어

- 타이밍 멈추기는 멈춘 직후 `정확/훌륭/좋음/아쉬움` 등급, 점수, 중앙 오차를 중복 없이 한 개의 결과 카드로 보여준다. 결과가 기록된 뒤에만 다음 참가자 버튼을 활성화하고 이 계약에 맞춰 회귀 테스트를 통과시킨다.
- 총액을 1원 이상 100,000,000원 이하의 정수로 제한하고 경계·연속 입력을 테스트한다.
- `settlement_started`, `game_started`, `settlement_completed`, `share_completed`, `storage_failed`의 의미와 중복 방지 규칙을 확정한다.
- 최근 모임 선택부터 게임 시작, 전체 결과 공유까지의 시간 구간을 측정한다.
- 로컬 테스트에서 TDS 아이콘 네트워크 요청과 safe-area 로그를 격리해 실패 신호를 읽을 수 있게 한다.
- 실제 AppsInToss 기기에서 초안·정산 저장 유지와 공유·이미지 저장·텍스트 복사 폴백을 검증한다.
- 최근 모임을 선택하면 선택 항목인 제목과 참여자 입력을 건너뛰고 금액 입력으로 이동한다.
- 참가자 교대 화면을 이전 기록을 가리는 휴대폰 전달 보호막으로 만든다.
- 최종 결과에 접을 수 있는 계산·공정성 영수증을 추가한다.

### 2차: 모임 기억과 반복 사용 루프

- 로컬 `Group`과 `Participant`에 UUID를 부여한다.
- 기존 이름 조합 기록을 완전 일치할 때만 자동 연결하고, 충돌·일부 인원 차이는 사용자 확인을 거친다.
- 구성 변경은 기존 모임을 덮어쓰지 않고 복제하며, 변환 실패 원본은 읽기 전용으로 보존한다.
- 현재 인원으로 완료 가능하고 120초 안에 끝나는 게임을 후보로 삼아 직전 게임을 가능하면 제외한다.
- 추천 게임 한 장을 먼저 보여주고 전체 게임 선택권을 유지한다.
- 최소 3회 이후 최근 6회의 추가 부담 횟수와 금액 합계를 접힌 영역으로 보여준다.
- 공정성 통계는 추천, 무작위 결과, 실력 게임 점수에 영향을 주지 않는다.
- 최근 모임 카드에 지난 게임·결과·경과일을 중립적인 한 줄로 보여주고 추천 이유와 연결한다.

## Rollout Sequence

```text
1차: 테스트·입력·측정·실기기 검증
        + 전달 보호막 + 계산 영수증
                    ↓ 현장 관찰
2차 A: Group/Participant UUID + 안전한 마이그레이션
                    ↓ 내부 게이트
2차 B: 추천 게임
                    ↓ 내부 게이트
2차 C/D: 누적 공정성 / 한 줄 기억을 각각 독립 출시
                    ↓
4~6주 반복 사용 검증
```

1차와 2차는 같은 계획에 속하지만 별도 출시 단위다. 2차 범위는 승인됐지만 아래 Go/No-Go 조건을 통과하기 전에는 구현을 시작하지 않는다. 2차 데이터 구조가 1차 현장 검증 실패의 원인을 가리지 않게 한다.

## Phase Gates

### 1차 출시 조건

- `npm test` 전체 통과, `npm run build` 성공, 해결되지 않은 P1 결함 0개다.
- 테스트 실행 중 실제 네트워크 요청과 처리되지 않은 React 상태 경고가 0개다. AppsInToss safe-area 비지원 로그는 별도 모킹으로 제거한다.
- AppsInToss 샌드박스가 지원하는 Android 실기기 1대와 iOS 실기기 1대에서 앱 종료·재실행과 앱 업데이트 뒤 초안 및 완료 기록 유지가 확인된다.
- 두 OS 모두에서 토스 공유, 이미지 저장, 텍스트 복사의 성공·취소·실패 상태를 각각 확인한다. 이 실기기 매트릭스를 통과하기 전에는 확인하지 않은 OS에 외부 출시하지 않는다.

### 2차 진입 조건

- 실제 4인 모임 최소 2회가 도움 없이 전체 흐름을 완료한다.
- 두 세션 모두 앱 실행부터 공유 완료까지 3분 이내이고, 최근 모임 사용 세션은 모임 선택부터 `game_started`까지 45초 이내다.
- 두 세션의 `8 participant-session observations` 중 최소 7건에서 참가자가 자신의 금액과 계산 이유를 별도 설명 없이 맞게 말한다. 같은 사람이 두 세션에 참여하면 두 관측으로 센다.
- 해결되지 않은 저장·계산·공유 P1 결함이 0개다.
- 다음 만남이 예정된 모임 최소 3개를 모집하고 반복 사용 관찰 일정이 확보된다.

조건을 충족하지 못하면 2차 구현을 시작하지 않고 1차 흐름의 마찰을 먼저 수정한다. 2차 기능을 이미 승인했다는 사실은 이 증거 게이트를 우회하지 않는다.

### 2차 내부 출시 조건

- 2차 A의 UUID·마이그레이션을 먼저 출시하고, 실제 보유 데이터 변환과 두 번의 정상 재실행에서 기록 손실·중복·잘못된 연결이 0건일 때만 2차 B를 켠다.
- 추천 게임은 독립 기능 플래그로 출시한다. 최소 3개 모임의 선택률·변경률과 인터뷰를 확인한 뒤에만 공정성 요약 또는 한 줄 기억 실험으로 넘어간다.
- 공정성 요약과 한 줄 기억은 서로 다른 기능 플래그를 사용하고 같은 세션에서 처음 노출하지 않는다. 각 효과와 부정 반응을 따로 판정한다.

## Operational Definitions

- `최근 모임`: 같은 로컬 기기에서 완료 기록이 있고 `completedAt`이 가장 최신인 최대 2개 모임이다.
- `완전 일치`: 참여자 이름에 앞뒤 공백 제거, 연속 공백 축약, Unicode NFC, 라틴 문자 소문자화를 적용한 뒤 한국어 로케일로 정렬한 집합이 동일한 상태다. 정규화 충돌이 있으면 완전 일치가 아니다.
- `완료 가능한 게임`: 현재 참가자 수가 `recommendedPlayers.min..max` 안에 있고 필수 런타임 API가 지원되는 게임이다.
- `예상 시간`: 1차에는 `estimatedSecondsPerPlayer × 참가자 수 + 15초`의 정적 메타데이터를 사용한다. 현장 관찰 전에는 실제 사용자 시간으로 자동 보정하지 않는다.
- `기본 균등 배분`: 현재 모임의 고정 표시 순서대로 `floor(총액 ÷ 인원수)`를 배분하고, 나머지 1원씩을 앞에서부터 더한 게임 미적용 기준액이다.
- `추가 부담`: 최종 부담액에서 기본 균등 배분액을 뺀 양수 부분이다. 정상 정수 나머지, 면제·할인, 동일 금액은 추가 부담으로 세지 않고 양수 초과분만 합산한다.
- `공정성 요약`: 최근 완료 6건에서 참여자별 추가 부담 횟수와 추가 부담 금액 합계만 계산한 읽기 전용 통계다.
- `중립적인 한 줄`: 사실과 시점만 말하고 승자·패자를 조롱하거나 성격을 평가하지 않는다. 예: `14일 전 · 반응속도 · 영희 님 면제`.

## Minimal Data Model

```text
Participant { id, displayName, normalizedName, createdAt }
Group { id, displayName, schemaVersion, createdAt, lastUsedAt }
  ├── GroupMember { groupId, participantId, displayOrder, active }
  └── Settlement { id, groupId, completedAt, amount, mode, gameId }
        ├── GameRun { id, settlementId, scores, rematchCount }
        └── BurdenOutcome { settlementId, participantId, role, amount }
```

- 식별 보장은 동일한 로컬 기기 안에서 사용자가 확인한 모임과 참여자에 한정한다. UUID는 기기 간 동일 인물 판별을 보장하지 않는다.
- 이름 변경은 같은 `participantId`의 표시 이름만 바꾼다. 동명이인·정규화 충돌·일부 인원 차이는 총무가 기존 참여자 연결 또는 새 참여자 생성을 직접 선택한다.
- 최근 모임 선택 시 기본 액션은 `그대로 사용 → 금액 입력`이며, 보조 액션 `멤버 수정`은 기존 모임을 덮어쓰지 않고 구성 변경 모임을 복제한다.
- 모임 복제는 사용자가 동일 인물로 확인한 `participantId`와 표시 순서를 재사용하고 추가 인원만 새 UUID를 만든다. 따라서 기존 참여자의 이력은 이어지고, 확인하지 않은 이름 유사성만으로 이력을 연결하지 않는다.
- Group 삭제는 해당 GroupMember와 Settlement·GameRun·BurdenOutcome 계층을 한 번에 삭제한다. Participant는 다른 GroupMember나 BurdenOutcome에서 참조하지 않을 때만 고아 정리하며, 공유 참여자와 다른 모임의 이력은 유지한다. 개별 Settlement 삭제도 지원한다.

## Migration Contract

1. 현재 데이터는 `schemaVersion: 1`, 새 데이터는 `schemaVersion: 2`로 구분한다.
2. 마이그레이션 시작 전 기존 JSON 전체를 변경 불가능한 `migration-backup:v1` 키에 복사한다.
3. 별도 임시 키에 v2 후보를 생성하고 레코드 수, settlement ID 집합, settlement별 필드 해시, 참여자별 금액 합계, GroupMember·Settlement·GameRun·BurdenOutcome의 참조 무결성이 원본과 일치하는지 검증한다.
4. 완전 일치하는 이름 집합만 자동 연결한다. 충돌은 `needs_confirmation` 상태로 남기고 원본을 읽기 전용으로 표시한다.
5. 저장소는 `@apps-in-toss/web-framework`의 `Storage` 키-값 API를 사용한다. 다중 키 트랜잭션을 가정하지 않고, 백업과 체크섬이 포함된 v2 후보를 각각 쓰고 다시 읽어 검증한 뒤 마지막 단일 `setItem`으로 활성 매니페스트를 v2 후보 키로 바꾼다. 같은 마이그레이션을 다시 실행해도 중복 UUID나 기록이 생기지 않아야 한다.
6. 앱 종료·저장 실패·검증 실패가 발생하면 활성 포인터를 바꾸지 않고 v1을 계속 읽는다. 다음 실행에서 재시도할 수 있다.
7. v1 원본·백업·v2 후보를 동시에 보관해 일시적으로 최대 약 3배 공간이 필요하다. 별도 용량 조회 API가 없으므로 각 쓰기 실패를 quota 실패로 취급하고 후보만 정리한 뒤 v1을 유지한다. 백업 쓰기 자체가 실패하면 마이그레이션을 시작하지 않는다.
8. 사용자가 복구를 선택하면 v2 후보를 폐기하고 백업으로 돌아간다. v2로 두 번 연속 정상 실행해 전체 검증을 통과하면 백업을 삭제하고 성공 상태를 기록한다. 전체 데이터 삭제는 후보·활성 매니페스트·마이그레이션 백업을 즉시 함께 삭제한다.

필수 테스트는 정상 변환, 빈 기록, 손상 기록, 동명이인, 이름 변경, 일부 인원 차이, 중간 종료, 저장 실패, 반복 실행, 롤백이다.

## Recommendation Contract

```text
candidates = games
  .filter(playerCount supported)
  .filter(runtime APIs supported)
  .filter(static estimated total <= 120s)

if candidates is empty but runtime-compatible player-compatible games exist:
  show those games with an honest duration warning
else if no runtime-compatible player-compatible game exists:
  show an unavailable state and do not allow game start
else if candidates has more than one:
  exclude the group's immediately previous game when possible

sort by group usage count ascending
then estimated total ascending
then catalog order ascending
recommend first
```

추천 입력은 참가자 수, 런타임 지원 여부, 정적 예상 시간, 직전 게임, 모임별 게임 사용 횟수뿐이다. 참여자별 금액, 부담 횟수, 승패, 점수, 공정성 통계는 직접·간접적으로 추천에 사용하지 않는다.

## Calculation Receipt Contract

- 기본 상태는 접힘이며 제목은 `어떻게 계산됐나요?`다.
- 펼치면 게임 결과, 적용 정산 방식, 선택된 참여자, 정수 배분 공식, 잔액 배분 순서, 참여자별 금액, 합계 검증을 보여준다.
- 기본 나머지는 현재 모임의 고정 표시 순서 앞에서부터 1원씩 배분하고, 같은 정산을 재렌더링·재시도해도 순서가 바뀌지 않는다. 예: `60,001원 ÷ 3명 → 20,000원씩 + 첫 번째 참여자 1원`, `20,001 + 20,000 + 20,000 = 60,001원`.
- 합계가 입력 총액과 다르면 결과를 저장·공유하지 않고 명명된 `settlement_total_mismatch` 오류를 표시한다.
- 접힘·펼침, 나누어떨어지는 값, 1원 잔액, 최솟값, 1억 원, 모든 정산 모드를 테스트한다.

## Event Contract

| Event | Emission | Deduplication key | Allowed properties |
|---|---|---|---|
| `settlement_started` | 신규·최근 모임 흐름 진입 | `appSessionId + settlementAttemptId` | source, participant_count |
| `game_started` | 실제 첫 게임 입력이 가능해진 시점 | `settlementAttemptId + gameRunId` | game_id, participant_count, duration_bucket |
| `settlement_completed` | 합계 검증된 결과가 화면에 표시됨 | `settlementId` | mode, game_id, participant_count, amount_bucket, duration_bucket |
| `share_completed` | 사용자가 고른 공유·저장·복사 액션 성공 | `settlementId + share_method` | share_method, duration_bucket |
| `storage_failed` | 읽기·쓰기·마이그레이션 최종 실패 | `appSessionId + operation + recordId` | stage, failure_reason |

- 전송 대상은 현재 프로젝트에 이미 설치된 Amplitude Browser SDK와 `VITE_AMPLITUDE_API_KEY`다. 키가 비어 있으면 전송하지 않고 이벤트 계약과 단위 테스트만 유지한다.
- 모든 `duration_bucket`은 동일한 `settlement_started` monotonic timestamp를 시작점으로 삼고 각 이벤트 발생 시점까지의 경과 시간으로 계산한다. 버킷은 `<45s`, `45-89s`, `90-179s`, `180s+`다. 앱 백그라운드 시간도 사용자가 체감한 총시간에 포함한다.
- `appSessionId`, `settlementAttemptId`, `gameRunId`, `settlementId`는 기기 내부 중복 방지에만 사용하고 분석 속성으로 전송하지 않는다.
- 이름, 제목, 정확한 금액, 모임·참여자 UUID, 공유 본문은 분석 이벤트에 포함하지 않는다.
- 최초 명시적 분석 동의 전에는 Amplitude SDK를 초기화하거나 어떤 이벤트도 전송하지 않는다. 동의 거절은 게임·계산·저장·공유 기능을 제한하지 않으며 설정에서 언제든 변경할 수 있다.
- 분석 동의가 꺼져 있거나 API 키가 없으면 이벤트는 전송하지 않는다. 현장 검증자는 별도 관찰표에 시작·게임 시작·공유 완료 시각과 성공 여부만 기록한다.
- 초기 현장 검증의 증거 원본은 연구자 관찰표다. 별도 분석 서버나 로컬 데이터 내보내기는 이번 범위가 아니다.

## Privacy and Retention

- 기록은 동일 로컬 기기에만 저장하며 자동 만료시키지 않는다. 사용자는 설정에서 전체 데이터, 모임 단위, 개별 정산 단위로 삭제할 수 있다.
- 모임·전체 삭제는 영향 범위를 보여주는 확인 대화상자를 거치며 완료 뒤 관련 통계와 추천 캐시도 제거한다.
- v2 전환 뒤 백업 보존 기간에 모임 또는 개별 정산 삭제가 요청되면 먼저 활성 v2의 전체 검증을 다시 통과시키고 롤백 권한과 v1 백업을 폐기한 뒤 삭제한다. 어느 단계라도 실패하면 삭제를 완료한 것으로 표시하지 않는다. 이 규칙으로 사용자가 삭제한 기록이 이후 롤백에서 복구되는 일을 막는다.
- 과거 정확한 금액과 공정성 요약은 기본 접힘 상태다. 공유 본문에는 이번 정산 외의 과거 금액을 포함하지 않는다.
- 삭제, 부분 삭제, 삭제 실패 롤백, 마이그레이션 백업 삭제 시점을 테스트한다.

## Success Criteria

### 1차

- 실제 4인 모임이 도움 없이 앱 실행부터 결과 공유까지 3분 안에 완료한다.
- 최근 모임 선택부터 `game_started`까지 45초 이내다.
- 네 명 모두 자신의 금액과 계산 이유를 별도 설명 없이 말할 수 있다.
- 토스 공유 실패 시 이미지 저장 또는 텍스트 복사를 사용자가 선택해 완료한다.
- 저장 실패가 게임·계산을 막지 않으며 사용자에게 기록이 남지 않음을 알린다.

### 2차

- 다음 일정이 잡힌 최소 3개 모임 중 2개 이상이 다음 결제 때 자발적으로 재사용한다.
- 표본은 통계적 최적화가 아니라 방향성 발견에만 사용한다. 추천 기본값을 전체 사용자에게 고정하려면 최소 10개 모임·20회 반복 세션을 별도로 확보한다.
- 추천 게임 선택률, 추천 변경률, 게임별 완료율, 공유 완료율을 측정한다.
- 두 번째 사용 뒤 `이름 재입력 절감`, `다른 게임 추천`, `지난 기록`, `공정성 요약` 중 무엇이 다시 사용한 이유였는지 각각 묻는다.
- 한 줄 기억은 최근 모임 재진입과 추천 이해를 돕는다는 가설로 평가하며, 불쾌·조롱·낙인 반응이 한 번이라도 나오면 기본 노출을 중단하고 문구를 재검토한다.
- 이름 변경·구성 변경·손상 기록에서 기존 완료 기록을 잃지 않는다.
- 공정성 통계를 처음 본 모든 관찰 대상자가 `이 통계가 다음 게임이나 금액에 영향을 주나요?`에 `영향을 주지 않는다`고 답해야 통과한다. 한 명이라도 오답이면 기본 노출을 중단하고 설명 문구를 다시 검증한다.

## NOT in Scope

- 참가자 전원 가입과 다중 기기 실시간 플레이: 한 명·한 기기라는 좁은 진입 구조를 유지한다.
- 서버 동기화와 공유 장부: 초기 반복 사용은 기기 로컬에서 검증한다.
- 직접 송금, 계좌 연결, 송금 독촉: 실제 반복 요청이 확인된 뒤 별도 실험으로 판단한다.
- OCR, 카드 문자 인식, 여행 경비 장부: 경쟁 제품의 기능 폭을 따라가지 않는다.
- 과거 부담 이력으로 추천 확률·무작위 결과·실력 점수를 조작하는 기능: 투명성 원칙과 충돌한다.
- `App.jsx` 전면 재작성: 필요한 경계만 추출하고 현장 학습 전에 플랫폼 재구축을 하지 않는다.

## Section 2 — Error and Rescue Contract

현재의 무명 `catch`와 오류 삼키기는 디버깅과 사용자 안내를 어렵게 하므로 경계 어댑터에서 다음 명명된 오류로 변환한다. 원본 이름·금액·공유 본문은 로그에 넣지 않는다.

| Method / codepath | What can go wrong | Error class |
|---|---|---|
| `repository.load` | 브리지 거부, JSON 손상, 스키마 불일치, 과대 payload | `StorageReadError`, `StoredDataCorrupt`, `SchemaMismatch`, `StoragePayloadTooLarge` |
| `repository.save` | quota, 브리지 거부, 직렬 큐 실패 | `StorageQuotaExceeded`, `StorageWriteError` |
| `migration.run` | 백업/후보 쓰기 실패, 체크섬·참조 불일치, 중간 종료 | `MigrationBackupError`, `MigrationInvariantError`, `MigrationInterrupted` |
| `calculateSettlement` | 잘못된 입력, 합계 불일치 | `SettlementInputInvalid`, `SettlementTotalMismatch` |
| `recommendGame` | 호환 게임 없음, 잘못된 메타데이터 | `NoCompatibleGame`, `GameMetadataInvalid` |
| `createSettlementImage` | canvas·blob·base64 실패 | `ImageRenderError`, `ImageEncodeError` |
| share pipeline | 사용자 취소, 브리지 미지원, 전달 실패 | `ShareCanceled`, `ShareUnsupported`, `ShareDeliveryFailed` |
| Amplitude | SDK 로드·초기화·전송 실패 | `AnalyticsUnavailable` |
| ads | SDK 미지원·로드·표시 실패 | `AdUnavailable` |

| Exception | Rescued | Rescue action | User sees |
|---|---:|---|---|
| `StoredDataCorrupt` / `StoragePayloadTooLarge` | Y | 원본을 격리 키에 보존하고 빈 저장 상태로 계속 | `기록을 불러오지 못했지만 이번 정산은 계속할 수 있어요` |
| `StorageQuotaExceeded` / `StorageWriteError` | Y | 1회 재시도 후 저장 없는 세션으로 전환 | `이번 결과는 기기에 저장되지 않아요` |
| migration errors | Y | 후보 폐기, 기존 활성 스키마 유지 | `기존 기록을 그대로 사용해요`와 복구 액션 |
| `SettlementTotalMismatch` | Y | 저장·공유 차단, 오류 코드 표시 | `금액 합계가 맞지 않아 결과를 만들 수 없어요` |
| `NoCompatibleGame` | Y | 게임 시작 차단, 정산 방식으로 돌아가기 | `이 기기에서 실행할 수 있는 게임이 없어요` |
| `ShareCanceled` | Y | 성공 이벤트 없음, 공유 시트 유지 | 오류 토스트 없음 |
| `ShareDeliveryFailed` | Y | 결과 유지, 재시도 제공 | `공유하지 못했어요. 다시 시도해 주세요` |
| analytics / ads errors | Y | 해당 부가 기능만 비활성화 | 핵심 흐름에는 아무 오류도 표시하지 않음 |

- 재시도는 Storage의 일시적 읽기·쓰기 실패에만 최대 1회 적용한다. 사용자 취소, 스키마 불일치, 계산 불변식 실패에는 자동 재시도하지 않는다.
- 모든 오류는 `operation`, `stage`, `appVersion`, `schemaVersion`, 명명된 `failureReason`을 가진 결과로 상위 계층에 전달한다. `catch {}`로 지우거나 손상 원본을 즉시 삭제하지 않는다.

## Section 3 — Security and Threat Model

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| 과대·손상 로컬 JSON으로 파싱 중 멈춤 또는 기록 소실 | Medium | High | 읽기 전 payload 크기 제한, 엄격한 스키마 검증, 격리 보존, 활성 포인터 유지 |
| 이름·제목에 제어문자·비정상 Unicode·공유 텍스트 삽입 | Medium | Medium | NFC 정규화, 제어문자 제거, grapheme 길이 제한, React 텍스트 렌더링과 canvas 문자열 처리만 사용 |
| 정확한 금액·이름·UUID의 분석 유출 | Low | High | 최초 opt-in, 이벤트 allowlist, 버킷만 전송, 전송 직전 금지 필드 테스트 |
| 마이그레이션 백업에 삭제 데이터 잔존 | Medium | High | 두 번의 정상 실행 뒤 폐기, 부분 삭제 전 롤백 종료, 전체 삭제 시 모든 후보·백업 제거 |
| 클라이언트 번들 키를 비밀로 오인 | Medium | Medium | Amplitude 키와 광고 그룹 ID는 공개 식별자로만 취급하고 결제·관리 비밀을 클라이언트에 두지 않음 |
| 조작된 UUID로 다른 사용자 데이터 접근 | Low | Low | 서버·다른 기기 데이터가 없고 조회 범위는 활성 로컬 매니페스트로 제한; 존재하지 않는 참조는 거부 |

- 총액은 숫자 키패드에서 생성된 `Number.isSafeInteger` 값 1..100,000,000만 허용한다.
- 제목은 앞뒤 공백을 제거한 최대 40 grapheme, 참여자 이름은 최대 20 grapheme로 제한한다. 빈 이름, C0/C1 제어문자, 정규화 뒤 중복 이름은 명시적으로 거부하고 이유를 보여준다.
- 공유·파일명·한 줄 기억은 HTML을 만들지 않고 텍스트로만 렌더링한다. 새 npm 패키지는 추가하지 않으며 기존 lockfile을 CI에서 고정 설치한다.
- 결제 계좌·로그인·서버 인증은 범위 밖이다. 민감 작업의 감사 흔적은 원격 로그가 아니라 PII 없는 로컬 진단 코드와 사용자 확인 대화상자로 제한한다.

## Section 4 — Data and Interaction Edge Cases

```text
INPUT ──▶ VALIDATE ──▶ NORMALIZE ──▶ DOMAIN ──▶ PERSIST ──▶ OUTPUT
  │           │             │            │          │           │
  ├ nil       ├ 범위/타입    ├ NFC/공백    ├ 불변식    ├ quota     ├ stale
  ├ empty     ├ 길이        ├ 이름 충돌   ├ no game   ├ 중복 ID   ├ partial
  └ rapid tap └ 정수 여부    └ 순서 고정   └ mismatch  └ interrupt └ encoding
```

| Interaction / data | Edge case | Handling and test |
|---|---|---|
| 금액 키패드 | 연속 입력·빠른 금액으로 1억 초과 | 다음 값을 계산하기 전에 clamp하지 않고 거부, 경계 99,999,999/100,000,000/100,000,001 테스트 |
| 참여자 입력 | 공백·동명이인·조합형/분해형 한글·20 grapheme 초과 | 정규화 후 오류 메시지, 원문 임의 병합 금지 |
| 최근 모임 | 기록 삭제 직후 오래된 카드 클릭 | ID 재조회 후 없으면 홈 갱신, 금액 화면으로 이동하지 않음 |
| 제출·게임 시작 | 빠른 두 번 누르기 | 첫 전이와 비동기 작업 동안 버튼 잠금, attempt ID로 중복 이벤트·저장 방지 |
| 전달 보호막 | 이전 참가자가 뒤로가기·앱 전환 | 점수 숨김 유지, 활성 턴 폐기 후 같은 참가자부터 재시작 |
| 게임 완료 | 동점·재경기 중 이탈·중복 점수 | reducer가 예상 참가자와 session ID를 검증, 중복 action 무시 및 진단 코드 기록 |
| 계산 | 1원·1억·나머지·면제 대상 누락 | 순수 함수가 합계 불변식을 반환, 실패 시 저장·공유 차단 |
| 저장·마이그레이션 | 앱 종료·quota·후보 중복 | idempotency key, read-back 검증, 기존 매니페스트 유지 |
| 공유 | 취소·연속 탭·화면 이탈·모든 폴백 실패 | in-flight 잠금, 취소 비오류, 결과 유지, 재시도 가능 |
| 시간·기억 | 자정·시간대 변경·미래 timestamp | 절대 ISO 저장, 표시 시 로컬 날짜 계산, 미래 값은 `최근`으로 clamp |
| 삭제 | 공유 Participant·롤백 백업 | 참조 없는 Participant만 정리, 삭제 전 백업 폐기 계약 적용 |

- 비동기 작업은 화면 unmount 뒤 React 상태를 갱신하지 않도록 취소 토큰 또는 활성 attempt 검사를 사용한다.
- 목록은 현재 기기 데이터만 다루지만 최근 화면은 인덱스 기반 상위 항목만 읽고, 1,000건 fixture에서도 정렬과 선택이 결정적인지 검증한다.

## Section 5 — Code Quality Contract

- `App.jsx`의 새 분기는 5개를 넘기지 않는다. 상태 전이는 `settlement/flow-controller`, 계산은 순수 도메인, 네이티브 호출은 adapter로 이동한다.
- 이미 존재하지만 앱에서 사용하지 않는 `features/settlement/flow.js`를 별도 두 번째 상태 머신으로 키우지 않는다. 현재 `step` 흐름과 행동을 먼저 characterization test로 고정한 뒤 새 controller로 한 전이씩 옮기고, 동등성 확인 후 옛 상태 코드를 제거한다.
- `App.jsx` 내부의 공유 payload·링크·이미지 조립은 `results` 경계로, 게임 결과 레이블과 계산 영수증 투영은 `games/core` 또는 `results/receipt`로 이동한다. UI는 이미 계산된 view model만 받는다.
- Storage와 Share의 무명 `catch` 패턴은 Section 2의 typed result로 통일한다. UI 컴포넌트가 브리지 오류 형태를 직접 해석하지 않는다.
- `Participant`, `GroupMember`, `Settlement`, `GameRun`, `BurdenOutcome` 명칭은 문서·코드·저장 스키마에서 동일하게 사용한다. `group`, `recentGroup`, 이름 조합 ID를 같은 의미로 혼용하지 않는다.
- 새 상태관리·스키마·날짜·UUID 패키지는 도입하지 않는다. Web Crypto UUID와 현재 React reducer·adapter 패턴이면 충분하다.
- 생성 상태인 `.codegraph/daemon.pid`와 `node_modules/.vite/vitest/results.json`은 소스 추적에서 제거 대상으로 분류한다. `dist`는 실제 AppsInToss 업로드 절차가 추적 산출물을 요구하는지 확인한 뒤 CI artifact 또는 명시적 release artifact 중 하나로만 관리한다.

## Section 6 — Test Strategy

```text
NEW UX
  consent → recent group direct amount → handoff shield → timing result card
  → receipt → share fallbacks → delete controls
  → [2차] migration confirmation → recommendation → fairness / memory

NEW DATA
  v1 JSON → backup → v2 candidate → checksum → active manifest
  game result → invariant → receipt → settlement record → projections

NEW ASYNC / INTEGRATIONS
  Storage queue · Amplitude lazy init · OS share/save/clipboard · ads

NEW RESCUE
  corrupt/quota/interruption · no compatible game · total mismatch
  · share cancel/failure · analytics/ads unavailable
```

| Area | Unit | Integration | Device / system |
|---|---|---|---|
| amount and names | 모든 경계·Unicode·중복 | 오류 문구와 다음 버튼 | 실제 한글 키보드 입력 |
| flow and handoff | 모든 reducer 전이·금지 전이 | 이전 결과 비노출, 뒤로가기, background | 4인 순차 전달 |
| timing result | 점수·등급 경계 | countdown 뒤 카드와 다음 버튼 | 60/120Hz 기기 |
| receipt | 모든 모드·1원 나머지·합계 property loop | 접힘/펼침·공유 차단 | 스크린리더 읽기 순서 |
| migration | golden v1 fixtures, idempotency, hashes | 각 Storage 작업 실패 주입 | 앱 강제 종료·업데이트 후 복구 |
| recommendation | 후보 없음·동률 정렬·직전 제외 | 추천 변경과 전체 목록 | reduced-motion 환경 |
| fairness / memory | 0/1/2/3/6/7회, 삭제 후 재계산 | 기능 플래그 독립 노출 | 관찰 인터뷰 |
| analytics | consent, allowlist, dedup, duration | 동의 전 SDK 미초기화 | Sandbox 네트워크 상태 |
| sharing | 각 폴백과 취소 | in-flight 중복 탭 | Android·iOS 전체 폴백 |

- 배포 자신감 테스트: `v1 데이터 → 중간 종료 → 재실행 → 원본 유지 → v2 성공 → 부분 삭제 → 롤백으로 부활하지 않음`을 한 통합 시나리오로 고정한다.
- 적대적 QA 테스트: 8명의 정규화 충돌 이름, 1억 원, 모든 공유 브리지 실패, 빠른 10회 탭에서도 한 건만 저장·추적되는지 검증한다.
- chaos 테스트: 마이그레이션의 매 `getItem/setItem/removeItem` 지점에서 하나씩 실패를 주입하고 활성 매니페스트가 항상 읽을 수 있는 스키마를 가리키는지 확인한다.
- 시간·난수·`requestAnimationFrame`은 fake clock과 주입 가능한 random source를 사용한다. TDS 아이콘과 네이티브 safe-area는 테스트에서 네트워크·브리지 adapter를 모킹해 실제 요청과 `act()` 경고를 0개로 만든다.
- 피라미드는 순수 함수 단위 테스트 다수, 화면 통합 테스트 소수, Android·iOS 핵심 여정 수동 E2E 각각 1세트로 유지한다. LLM·프롬프트 변경은 없다.

## Section 7 — Performance Budget

- 현재 기준 빌드는 JS 1,314.27 kB, gzip 420.46 kB이며 Vite 단일 청크 경고가 발생한다. 새 기능이 초기 gzip을 5% 이상 늘리거나 450 kB를 넘으면 실패시키는 bundle budget을 CI에 둔다.
- 홈에 필요하지 않은 게임 화면, 기록·설정, 2차 공정성·기억 투영은 lazy chunk로 분리한다. Amplitude는 동의 뒤 동적 import를 유지한다.
- 가장 느린 예상 경로는 초기 JS 해석, v1→v2 JSON 변환, 1080×1350 PNG 생성이다. 각각 초기 chunk 분리, 1,000건 migration benchmark, 공유 액션 시점의 지연 생성으로 격리한다.
- 최근 모임·최근 6회 공정성은 전체 settlement 배열을 매 render마다 정렬하지 않고 repository가 유지하는 group index에서 읽는다. 파생 결과는 활성 매니페스트 버전과 settlement ID 집합을 키로 memoize한다.
- 10배 데이터에서는 키 단위 group/settlement 저장으로 전체 배열 재쓰기를 피한다. 100배 데이터가 현실화되면 Storage가 첫 병목이며 서버를 미리 만들지 않고 5,000건 fixture에서 경고·내보내기 요구를 재평가한다.
- DB, Redis, HTTP background job, connection pool은 추가되지 않아 N+1·인덱스·큐 압력은 해당 없음이다.

## Section 8 — Observability and Debuggability

| Signal | Working | Broken |
|---|---|---|
| core funnel | started → game_started → completed → shared 전환율·시간 | 단계 이탈 또는 3분 초과 증가 |
| storage | 저장 성공과 schemaVersion | `storage_failed` by stage/reason, migration rollback |
| recommendation | 노출·선택·변경·완료 | 후보 없음·변경률 급증 |
| receipt | 펼침과 공유 완료 | `settlement_total_mismatch`, 설명 오답 |
| fairness / memory | 기능별 노출과 재사용 인터뷰 | 오해·불쾌 반응 1건 |

- 초기 파일럿의 source of truth는 이름·금액 없는 관찰표다. Amplitude는 opt-in 세션의 집계 보조 수단이며 개인 세션 재구성에 사용하지 않는다.
- 오류 화면에는 `STORAGE_READ`, `MIGRATION_INVARIANT`, `SHARE_DELIVERY`처럼 사람이 전달할 수 있는 안정적 진단 코드와 앱·스키마 버전만 보여준다.
- 기기에는 최근 50개의 PII 없는 진단 항목을 ring buffer로 보관하고 사용자가 `진단 정보 복사`를 누를 때만 앱 버전, OS, stage, failureReason을 복사한다. 이름·제목·정확한 금액·UUID는 제외한다.
- 파일럿 대시보드는 완료율, 중앙/최대 소요시간, 공유 폴백 비율, Storage 실패 수, 기능 플래그별 재사용을 표시한다. `SettlementTotalMismatch` 1건 또는 Storage 실패율 2% 초과는 출시 중단 조건이다.
- runbook은 저장 실패, migration invariant, 모든 공유 폴백 실패, 분석 SDK 실패, 광고 실패를 포함한다. 앞의 세 항목은 기능 중단·롤백 대상이고 분석·광고 실패는 핵심 흐름을 계속한다.

## Section 9 — Deployment and Rollout

현재 `.github` CI가 없으므로 첫 구현 작업에 `npm ci → npm test → npm run build → bundle budget`을 실행하는 최소 GitHub Actions 검증을 추가한다. 로컬 서버나 localhost 브라우저는 자동 검증 조건이 아니다.

```text
0. baseline blocker fix
   └─ 129 tests green + build + generated-file policy
1. Phase 1 flags only
   └─ Android/iOS Sandbox → 2 field sessions → Go/No-Go
2. Phase 2A identity/migration
   └─ staged device data → 2 clean launches → integrity gate
3. Phase 2B recommendation flag
   └─ 3 groups observation → selection/change interview
4. Phase 2C fairness OR 2D memory
   └─ separate first exposure → negative-signal stop rule
```

- 새 앱은 v1을 읽고 v2를 쓸 수 있는 호환 reader를 먼저 배포한 뒤 v2 활성 매니페스트를 만든다. 이전 v1-only 바이너리는 v2 백업 폐기 뒤 롤백 대상으로 사용하지 않는다.
- UI 기능 롤백은 해당 `VITE_ENABLE_*`을 끈 v2-compatible forward-fix 빌드로 수행한다. 데이터 롤백은 백업 보존 기간에만 v1로 전환하고, 이후에는 직전 검증 v2 매니페스트를 사용한다.
- Sandbox와 실제 배포 빌드는 같은 lockfile·build command를 사용하고 환경 변수 값만 다르게 한다. API 키가 없는 환경에서도 핵심 테스트와 빌드가 통과해야 한다.
- 배포 후 5분에는 앱 진입, 새 정산, 합계, 저장, 공유 시트, 오류 로그를 확인한다. 첫 1시간에는 Storage 실패·합계 불일치·공유 실패와 번들 로드 이상을 확인하고 중단 임계치를 넘으면 다음 단계 플래그를 켜지 않는다.
- `node_modules/.vite/vitest/results.json`과 `.codegraph/daemon.pid`는 Git 추적에서 제거한다. `dist`는 AppsInToss 업로드 도구가 소스 빌드를 수행할 수 있으면 CI artifact로 전환하고, 추적이 필수라면 release commit에서만 재생성해 소스 변경과 분리한다.
- 자동 smoke는 저장 adapter·계산·공유 fallback의 모킹 통합 테스트다. 네이티브 smoke는 Android/iOS 체크리스트에 실행자·앱 버전·OS·결과를 기록한다.

## Section 11 — Design and UX Intent

```text
HOME
 ├─ 첫 사용: 새 정산 → 제목(선택) → 금액 → 참여자 → 방식
 └─ 재사용: 최근 모임 ─────────────────────→ 금액
                                              ↓
                                      추천 게임 / 전체 보기
                                              ↓
              [다음 사람에게 전달] → [준비됐어요] → PLAY → TURN RESULT
                       ↑                                  │
                       └──────── 다음 참가자 ────────────┘
                                              ↓
                                  결과 → 계산 영수증 → 공유
                                              ↓
                            다음 방문: 한 줄 기억 + 새 추천
```

| Feature | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|

| receipt | 계산 중 버튼 잠금 | 해당 없음 | 저장·공유 차단 | 접힌 영수증 | 저장 실패여도 결과 표시 |

| share | 액션별 spinner | 해당 없음 | 재시도 | 성공 확인 | 다음 폴백 선택 |

- 감정 곡선은 `빠르게 시작 → 차례 전 긴장 → 즉시 작은 성취 → 모두가 납득 → 단톡방 마무리`다. 과거 부담 통계가 게임의 재미보다 먼저 보이거나 사람을 평가하는 문구를 사용하지 않는다.
- 분석 동의는 첫 정산을 막는 시작 모달로 띄우지 않는다. 첫 완료 뒤 비차단 카드에서 목적·전송하지 않는 정보·거절 가능성을 설명하고 명시적으로 선택한 다음 세션부터만 추적한다.
- 최근 모임 카드의 주 액션은 전체 카드 탭 `그대로 사용`이고 `멤버 수정`은 보조 액션이다. 추천은 한 장만 강조하고 `다른 게임 보기`를 같은 화면에 둔다.
- 전달 보호막은 다음 참가자 이름과 `준비됐어요` 한 동작만 보여주며 이전 점수·금액·승패를 DOM에서도 렌더링하지 않는다. 결과 카드는 등급·점수·오차를 한 번만 말한다.
- 영수증은 결과와 공유 CTA 사이에 두고 기본 접힘으로 유지한다. 합계와 각자 금액은 접힌 상태에서도 보이며 상세 규칙만 펼친다.
- TDS `Top`, `ListRow`, `BottomCTA`, `BottomSheet`, `ConfirmDialog`를 우선하고 44px 이상 터치 영역, 명시적 label, focus-visible, `aria-live` 중복 억제, 320~430px 폭과 safe-area를 검증한다.
- `prefers-reduced-motion`에서는 장식 애니메이션을 제거하고 타이밍처럼 움직임이 본질인 게임은 추천 후보에서 제외해 대체 게임을 제시한다. 사용자가 직접 고르면 움직임 필요성을 시작 전에 알린다.
- 모바일 세로 화면을 기준으로 한 화면에 주 CTA 하나만 둔다. 공유·저장 실패에서도 계산 결과는 사라지지 않는다.
- 구현 전 `/plan-design-review`, 구현 후 실제 Android·iOS 화면으로 `/design-review`를 수행하는 것이 권장된다.
